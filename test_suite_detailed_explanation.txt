PART 1 — WHAT PROBLEM DOES A TEST SUITE SOLVE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Without Test Suite:
    You test each page independently.
    Login page → tested alone.
    Goal Sheet page → tested alone.
    They never talk to each other.

  The Problem:
    Real users don't test pages in isolation.
    A real HR user does:
      Login → Go to Goal Sheet → Add 5 Goals → Submit Goals → Logout
    A real Lead user does:
      Login → Go to Goal Sheet → Review Goals → Approve Goals → Logout

    These are two different end-to-end journeys through the same pages,
    with different data and different outcomes. A Test Suite captures exactly
    this kind of multi-page, role-dependent journey.

  What a Test Suite IS:
    A directed graph (flowchart) where:
      - Each NODE  = one scenario on one page (one step in the journey)
      - Each EDGE  = the transition from one step to the next
      - Each CONDITION on an edge = the logic that chooses which path to take

PART 3 — NODES: WHAT THEY ARE AND HOW THEY WORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  A NODE is one box in the flowchart.

  Each node has 4 required pieces:
    id        — a unique string identifier within this flow_definition
    type      — what kind of node it is (see node types below)
    position  — where it sits on the canvas {x, y} in pixels
    data      — the payload: what this node represents

  ────────────────────────────────────────────────────────────────────────────
  3.1  THE 4 NODE TYPES
  ────────────────────────────────────────────────────────────────────────────

  TYPE 1: "start"
    ─────────────
    What it is:
      The entry point of the suite. Every flowchart has exactly ONE start node.
      It has no page or scenario attached — it just marks where execution begins.
    Visual:
      A green circle with the label "START"
    Rules:
      - Cannot be a target (nothing points TO it)
      - Can only have ONE outgoing edge
      - Cannot be deleted by the user

    Example:
      {
        "id": "node-start",
        "type": "start",
        "position": { "x": 400, "y": 0 },
        "data": {
          "label": "START",
          "node_type": "start",
          "page_id": null,
          "scenario_id": null
        }
      }

  ─────────────────────────────────────────────────────────────────────────────

  TYPE 2: "end"
    ───────────
    What it is:
      The exit point. A flowchart can have multiple END nodes (e.g., one for
      a passing path and one for a failing path). It marks where the suite stops.
    Visual:
      A red circle with the label "END"
    Rules:
      - Cannot be a source (nothing comes OUT of it)
      - Can have multiple nodes pointing TO it
      - Cannot be deleted by the user

    Example (pass end):
      {
        "id": "node-end-pass",
        "type": "end",
        "position": { "x": 200, "y": 900 },
        "data": {
          "label": "END — PASS",
          "node_type": "end",
          "page_id": null,
          "scenario_id": null
        }
      }

    Example (fail end — when login fails):
      {
        "id": "node-end-fail",
        "type": "end",
        "position": { "x": 700, "y": 300 },
        "data": {
          "label": "END — FAIL",
          "node_type": "end",
          "page_id": null,
          "scenario_id": null
        }
      }

  ─────────────────────────────────────────────────────────────────────────────

  TYPE 3: "step"
    ────────────
    What it is:
      A real action in the journey. Linked to a specific Page and Scenario
      from the AUTOTEST database. When this node is executed, it runs all
      test cases in that scenario and records their pass/fail results.
    Visual:
      A card showing the page title, scenario title, and colour-coded border
      based on the scenario category.
    Rules:
      - Must be linked to a page_id AND a scenario_id before status can be "ready"
      - Can have multiple incoming edges
      - Can have multiple outgoing edges (branching)
      - CAN be deleted

    Full example — Step 1 (Login):
      {
        "id": "node-1",
        "type": "step",
        "position": { "x": 400, "y": 120 },
        "data": {
          "label": "Login Page — Valid Login",
          "node_type": "step",
          "page_id": 1,
          "scenario_id": 10,
          "page_title": "Login Page",
          "scenario_title": "Valid Login - Auth Positive Flow",
          "category": "auth-positive"
        }
      }

    What "executing" this node means at runtime:
      1. The engine looks up Scenario 10 in the DB.
      2. It finds all TestCases under Scenario 10.
      3. It runs the Selenium script for Scenario 10.
      4. Each TestCase gets a TestExecution record: "passed" or "failed".
      5. If ALL TestCases pass → node outcome = "passed"
         If ANY TestCase fails  → node outcome = "failed"
      6. That outcome is stored in the execution engine's results map
         and used by branching logic on outgoing edges.

  ─────────────────────────────────────────────────────────────────────────────

  TYPE 4: "branch"
    ──────────────
    What it is:
      A decision diamond. It has NO page or scenario. Its only purpose is to
      route the flow to different paths based on conditions. It runs no tests.
    Visual:
      A diamond/rhombus shape with a label like "Role Check"
    Rules:
      - Has exactly one incoming edge
      - Has two or more outgoing edges (each with a condition)
      - Does NOT execute any test — just evaluates conditions and picks a path
      - CAN be deleted

    Example — Role Check after login:
      {
        "id": "node-branch-role",
        "type": "branch",
        "position": { "x": 400, "y": 400 },
        "data": {
          "label": "Role Check",
          "node_type": "branch",
          "page_id": null,
          "scenario_id": null
        }
      }

    NOTE: You can ALSO put branch conditions directly on edges out of a "step"
    node without needing a separate "branch" node. The branch node is optional —
    use it when the decision is conceptually separate from the test action.

PART 4 — EDGES: WHAT THEY ARE AND HOW THEY WORK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  An EDGE is an arrow connecting two nodes.
  It answers the question: "After this step, where do we go next — and under
  what condition?"

  Every edge has these fields:
    id        — unique string
    source    — the node_id this arrow comes FROM
    target    — the node_id this arrow points TO
    label     — (optional) human-readable text shown on the arrow in the UI
    condition — (optional) the branch logic object (see Part 5 for full detail)

  ────────────────────────────────────────────────────────────────────────────
  4.1  UNCONDITIONAL EDGE (always followed)
  ────────────────────────────────────────────────────────────────────────────

  When condition is null, the edge is ALWAYS followed.
  This is the default connection between sequential steps.

  Example — Start → Step 1 (always go to login first):
    {
      "id": "edge-start-to-login",
      "source": "node-start",
      "target": "node-1",
      "label": null,
      "condition": null
    }

  Example — Step 2 → Branch Node (always go to role check after dashboard):
    {
      "id": "edge-dashboard-to-branch",
      "source": "node-2",
      "target": "node-branch-role",
      "label": null,
      "condition": null
    }

  ────────────────────────────────────────────────────────────────────────────
  4.2  CONDITIONAL EDGE (followed only if condition is true)
  ────────────────────────────────────────────────────────────────────────────

  When condition is set, the edge is ONLY followed if the condition evaluates
  to true at runtime.

  Example — If login FAILED, go to the fail end node:
    {
      "id": "edge-login-to-end-fail",
      "source": "node-1",
      "target": "node-end-fail",
      "label": "Login failed",
      "condition": {
        "field": "_outcome",
        "op": "eq",
        "value": "failed"
      }
    }

  Example — If login PASSED, go to the dashboard:
    {
      "id": "edge-login-to-dashboard",
      "source": "node-1",
      "target": "node-2",
      "label": "Login passed",
      "condition": {
        "field": "_outcome",
        "op": "eq",
        "value": "passed"
      }
    }

  Example — If role is "employee", go to goal sheet (add goals):
    {
      "id": "edge-branch-to-employee-path",
      "source": "node-branch-role",
      "target": "node-3a",
      "label": "role = employee",
      "condition": {
        "field": "role",
        "op": "eq",
        "value": "employee"
      }
    }

  Example — If role is "lead", go to view goals:
    {
      "id": "edge-branch-to-lead-path",
      "source": "node-branch-role",
      "target": "node-4a",
      "label": "role = lead",
      "condition": {
        "field": "role",
        "op": "eq",
        "value": "lead"
      }
    }

  ────────────────────────────────────────────────────────────────────────────
  4.3  RULES FOR EDGES AT A BRANCH POINT
  ────────────────────────────────────────────────────────────────────────────

  When a node has MULTIPLE outgoing edges:
    1. The engine evaluates ALL conditional edges in order.
    2. It follows the FIRST one whose condition is TRUE.
    3. It then checks unconditional edges as a fallback (if no conditional matched).
    4. If nothing matches → that path simply ends (node becomes unreachable).

  Best practice:
    Always include a "default" unconditional edge as a fallback on branch nodes,
    or ensure conditions are exhaustive (employee | lead | hr_admin covers all roles).

PART 5 — BRANCH CONDITIONS: FULL SPECIFICATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  A condition is a JSON object with 3 fields:

    {
      "field": "...",   ← what to evaluate
      "op":    "...",   ← how to compare
      "value": "..."    ← what to compare against
    }

  ────────────────────────────────────────────────────────────────────────────
  5.1  THE "field" — What Are We Looking At?
  ────────────────────────────────────────────────────────────────────────────

  There are two kinds of fields:

  KIND A — Test data fields (runtime variables provided when triggering the run)
    These come from the test_data dict you pass when clicking "Run Suite".
    You define the field names yourself — they match the keys in test_data.

    Example test_data:
      {
        "role": "employee",
        "account_type": "corporate",
        "region": "APAC"
      }

    Field examples:
      "role"          → looks up test_data["role"]         → "employee"
      "account_type"  → looks up test_data["account_type"] → "corporate"
      "region"        → looks up test_data["region"]       → "APAC"

  KIND B — The special reserved field "_outcome"
    This refers to the RESULT of the most recently executed step node.
    It is automatically set by the execution engine after each step.

    Possible values:
      "passed"  → all test cases in that step's scenario passed
      "failed"  → one or more test cases failed
      "error"   → the script crashed (exception, driver error, etc.)
      "skipped" → the step had no scenario linked

    Example usage:
      After the Login step, use "_outcome" to branch:
        condition: { "field": "_outcome", "op": "eq", "value": "passed" }
        → "If login passed, continue to dashboard"

  ────────────────────────────────────────────────────────────────────────────
  5.2  THE "op" — Comparison Operators
  ────────────────────────────────────────────────────────────────────────────

  "eq"   — equals
    { "field": "role", "op": "eq", "value": "employee" }
    → true when test_data["role"] == "employee"

  "neq"  — not equals
    { "field": "role", "op": "neq", "value": "hr_admin" }
    → true when test_data["role"] != "hr_admin"
    → matches both "employee" and "lead" in one edge

  "in"   — value is in a comma-separated list
    { "field": "role", "op": "in", "value": "employee,lead" }
    → true when test_data["role"] is either "employee" OR "lead"
    → useful when two roles share the same path

  ────────────────────────────────────────────────────────────────────────────
  5.3  THE "value" — Always a String
  ────────────────────────────────────────────────────────────────────────────

  All condition values are strings. Even if you're comparing numbers,
  use a string. The engine compares strings.

    "value": "passed"       ← for _outcome
    "value": "employee"     ← for role
    "value": "3"            ← for a count-like field

  ────────────────────────────────────────────────────────────────────────────
  5.4  CONDITION EVALUATION PSEUDOCODE (inside the engine)
  ────────────────────────────────────────────────────────────────────────────

  def evaluate_condition(condition, test_data, last_node_outcome):
      field = condition["field"]
      op    = condition["op"]
      value = condition["value"]

      # Resolve the actual value to compare
      if field == "_outcome":
          actual = last_node_outcome    # "passed", "failed", "error", "skipped"
      else:
          actual = test_data.get(field, "")   # from the user-provided dict

      # Apply the operator
      if op == "eq":
          return actual == value
      elif op == "neq":
          return actual != value
      elif op == "in":
          allowed = [v.strip() for v in value.split(",")]
          return actual in allowed
      else:
          return False    # unknown operator → never match

PART 7 — HOW THE EXECUTION ENGINE WALKS THE GRAPH AT RUNTIME
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  When a user clicks "Run Suite", they provide test_data. The engine uses that
  + the outcome of each step to decide which path to follow.

  ────────────────────────────────────────────────────────────────────────────
  7.1  RUN WITH test_data = { "role": "employee" }
  ────────────────────────────────────────────────────────────────────────────

  Initial state:
    test_data    = { "role": "employee" }
    results      = {}              ← empty, no steps run yet
    queue        = [node-start]
    visited      = {}

  ── Iteration 1: node-start ────────────────────────────────────────────────
    Current node  = node-start  (type = "start")
    Action:       = do nothing (start node, no test to run)
    Outgoing edges:
      edge-start-to-login  (condition = null → unconditional, always follow)
    Add to queue: node-1
    queue = [node-1]

  ── Iteration 2: node-1 (Login Page — Valid Login) ──────────────────────────
    Current node  = node-1  (type = "step", scenario_id = 10)
    Action:
      Run all test cases in Scenario 10.
      All test cases pass.
    results["node-1"] = "passed"

    Outgoing edges from node-1:
      edge-login-fail:  condition { field="_outcome", op="eq", value="failed" }
        Evaluate: results["node-1"] == "failed"?  → "passed" == "failed"? → FALSE
        Skip this edge.

      edge-login-pass:  condition { field="_outcome", op="eq", value="passed" }
        Evaluate: results["node-1"] == "passed"?  → "passed" == "passed"? → TRUE
        Follow this edge.

    Add to queue: node-2
    queue = [node-2]

  ── Iteration 3: node-2 (HR Dashboard — View Dashboard Stats) ───────────────
    Current node  = node-2  (type = "step", scenario_id = 20)
    Action:
      Run all test cases in Scenario 20.
      All pass.
    results["node-2"] = "passed"

    Outgoing edges from node-2:
      edge-dashboard-to-branch:  condition = null → unconditional
        Always follow.

    Add to queue: node-branch-role
    queue = [node-branch-role]

  ── Iteration 4: node-branch-role (Role Check) ───────────────────────────────
    Current node  = node-branch-role  (type = "branch")
    Action:       = do nothing (branch node, no test to run)

    Outgoing edges from node-branch-role:
      edge-branch-employee:  condition { field="role", op="eq", value="employee" }
        Evaluate: test_data["role"] == "employee"?  → "employee" == "employee"? → TRUE
        Follow this edge. STOP evaluating other edges (first match wins).

    Add to queue: node-3a
    queue = [node-3a]

  ── Iteration 5: node-3a (Goal Sheet — Add 5 Goals) ─────────────────────────
    Current node  = node-3a  (type = "step", scenario_id = 30)
    Action:
      Run all test cases in Scenario 30 (adding 5 goals).
      All pass.
    results["node-3a"] = "passed"

    Outgoing edges from node-3a:
      edge-3a-to-3b:  condition = null → unconditional
    Add to queue: node-3b
    queue = [node-3b]

  ── Iteration 6: node-3b (Goal Sheet — Submit Goals) ────────────────────────
    Current node  = node-3b  (type = "step", scenario_id = 31)
    Action:
      Run all test cases in Scenario 31 (submitting goals).
      All pass.
    results["node-3b"] = "passed"

    Outgoing edges from node-3b:
      edge-3b-to-end:  condition = null → unconditional
    Add to queue: node-end-employee
    queue = [node-end-employee]

  ── Iteration 7: node-end-employee ───────────────────────────────────────────
    Current node = node-end-employee  (type = "end")
    Action:       = STOP. Suite execution complete.

  FINAL RESULTS for role=employee run:
    node-1  → passed  (Login)
    node-2  → passed  (Dashboard)
    node-3a → passed  (Add Goals)
    node-3b → passed  (Submit Goals)

    Nodes NOT visited: node-4a, node-4b, node-5a, node-5b
    (These are on different branches that were not taken)

    Summary: total=4, passed=4, failed=0, skipped=0
    TestSuiteRun.status = "passed"

  ────────────────────────────────────────────────────────────────────────────
  7.2  SAME SUITE, DIFFERENT RUN: test_data = { "role": "lead" }
  ────────────────────────────────────────────────────────────────────────────

  Everything is identical through node-2 (Dashboard).
  At node-branch-role:

    edge-branch-employee:  "lead" == "employee"? → FALSE  (skip)
    edge-branch-lead:      "lead" == "lead"?     → TRUE   (follow this one)

  Execution continues:
    node-4a (Goal Sheet — View Goals)    → passed
    node-4b (Approve Goals — Approve All) → passed
    node-end-lead → STOP

  Nodes NOT visited this time: node-3a, node-3b, node-5a, node-5b

  This demonstrates that the SAME flow_definition creates a DIFFERENT
  execution path at runtime based purely on the test_data provided.

  ────────────────────────────────────────────────────────────────────────────
  7.3  WHAT HAPPENS WHEN LOGIN FAILS
  ────────────────────────────────────────────────────────────────────────────

  test_data = { "role": "employee" }
  (Role doesn't matter — login fails before we get to role branching)

  node-1 (Login):  All test cases fail → results["node-1"] = "failed"

  Outgoing edges:
    edge-login-fail:  "_outcome" == "failed"? → TRUE  → follow this edge
    (edge-login-pass is not evaluated because first match was found)

  Execution continues to: node-end-fail → STOP immediately.

  Nodes visited: node-1 only.
  Summary: total=1, passed=0, failed=1, skipped=0
  TestSuiteRun.status = "failed"

PART 8 — HOW MULTIPLE EXECUTION FLOWS ARE CREATED FROM ONE SUITE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  The flow_definition is STATIC — it never changes between runs.
  What changes is the test_data you provide when triggering the run.

  One suite definition → infinite possible execution paths:

  Run #1:  test_data = { "role": "employee" }
    Path: START → Login → Dashboard → Add Goals → Submit Goals → END

  Run #2:  test_data = { "role": "lead" }
    Path: START → Login → Dashboard → View Goals → Approve Goals → END

  Run #3:  test_data = { "role": "hr_admin" }
    Path: START → Login → Dashboard → View Goals → Generate Report → END

  Run #4:  test_data = { "role": "employee" }  (but login fails this time)
    Path: START → Login → END (early exit on login fail)

  Run #5:  test_data = { "role": "unknown_role" }
    Path: START → Login → Dashboard → Role Branch → NO MATCH → END
    (None of the three role conditions match → the branch node has no
     valid exit → execution stops at the branch)

  Each run is stored as a separate TestSuiteRun row in the DB.
  Each run's individual test case results are stored as TestExecution rows
  with that run's test_suite_run_id.

  This means you can compare:
    "Login passed in 3 out of 5 recent runs for role=employee"
    "Goal submission failed in run #4 but passed in runs #1, #2, #3"

PART 10 — WHAT flow_definition CONTAINS (COMPLETE FIELD REFERENCE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  {
    "nodes": [                    ← array of all nodes in the flowchart
      {
        "id":       string,       ← REQUIRED. Unique within this flow_definition.
                                     Convention: "node-start", "node-1", "node-end"
        "type":     string,       ← REQUIRED. One of: "start" | "end" | "step" | "branch"
        "position": {             ← REQUIRED. Pixel position on the canvas.
          "x": number,
          "y": number
        },
        "data": {
          "label":         string,  ← REQUIRED. Shown as the node's title in the UI.
          "node_type":     string,  ← REQUIRED. Same value as outer "type".
          "page_id":       int|null, ← null for start/end/branch. Required for step.
          "scenario_id":   int|null, ← null for start/end/branch. Required for step.
          "page_title":    string|null, ← display only, copied from Page.page_title
          "scenario_title":string|null, ← display only, copied from TestScenario.title
          "category":      string|null  ← display only, copied from TestScenario.category
        }
      }
    ],

    "edges": [                    ← array of all directed connections
      {
        "id":        string,      ← REQUIRED. Unique within this flow_definition.
                                     Convention: "edge-{source_id}-to-{target_id}"
        "source":    string,      ← REQUIRED. node.id this arrow starts FROM.
        "target":    string,      ← REQUIRED. node.id this arrow points TO.
        "label":     string|null, ← Shown on the arrow in the UI. null = no label.
        "condition": {            ← null = unconditional (always follow).
          "field": string,        ← "_outcome" OR a key from test_data
          "op":    string,        ← "eq" | "neq" | "in"
          "value": string         ← the value to compare against
        } | null
      }
    ]
  }

  ────────────────────────────────────────────────────────────────────────────
  IMPORTANT RULES FOR A VALID flow_definition
  ────────────────────────────────────────────────────────────────────────────

  1. Exactly ONE "start" node must exist.
  2. At least ONE "end" node must exist (can have multiple).
  3. Every "step" node must have page_id AND scenario_id set (for "ready" status).
  4. "start" node must have no incoming edges.
  5. "end" nodes must have no outgoing edges.
  6. No cycles allowed (a node cannot eventually point back to itself).
  7. All edges must reference valid node IDs that exist in the nodes array.
  8. All node IDs and edge IDs must be unique within the flow_definition.

  The backend validates all of these rules when the suite status is set to "ready".

PART 11 — HOW THE EXECUTION ENGINE USES flow_definition STEP BY STEP
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  When process_test_suite_run() is called in the llm-service worker:

  STEP A — Load the suite from DB
    suite = db.query(TestSuite).filter_by(id=suite_id).first()
    flow  = suite.flow_definition   ← the JSON object from Part 6

  STEP B — Mark the run as started
    run.status = "running"
    run.started_on = datetime.utcnow()
    db.commit()

  STEP C — Find the start node
    start = next(n for n in flow["nodes"] if n["type"] == "start")

  STEP D — Build the adjacency map
    adj = {}
    for edge in flow["edges"]:
      if edge["source"] not in adj:
        adj[edge["source"]] = []
      adj[edge["source"]].append({
        "target":    edge["target"],
        "condition": edge["condition"]
      })

    After building adj for our example:
      adj = {
        "node-start":      [{ target: "node-1",           condition: null }],
        "node-1":          [{ target: "node-end-fail",     condition: { field:"_outcome", op:"eq", value:"failed" }},
                            { target: "node-2",            condition: { field:"_outcome", op:"eq", value:"passed" }}],
        "node-2":          [{ target: "node-branch-role",  condition: null }],
        "node-branch-role":[{ target: "node-3a",           condition: { field:"role", op:"eq", value:"employee" }},
                            { target: "node-4a",           condition: { field:"role", op:"eq", value:"lead" }},
                            { target: "node-5a",           condition: { field:"role", op:"eq", value:"hr_admin" }}],
        "node-3a":         [{ target: "node-3b",           condition: null }],
        "node-3b":         [{ target: "node-end-employee", condition: null }],
        "node-4a":         [{ target: "node-4b",           condition: null }],
        "node-4b":         [{ target: "node-end-lead",     condition: null }],
        "node-5a":         [{ target: "node-5b",           condition: null }],
        "node-5b":         [{ target: "node-end-hr",       condition: null }]
      }

  STEP E — Walk the graph (BFS)
    queue   = deque([ start_node ])
    visited = set()
    results = {}       ← filled as each step runs

    LOOP:
      node = queue.popleft()
      if node.id in visited: skip
      visited.add(node.id)

      IF node.type == "step":
        # Execute the scenario and record outcome
        outcome = execute_scenario(node.data.scenario_id, ...)
        results[node.id] = outcome
        notify_websocket(run_id, node.id, outcome)

      IF node.type == "end":
        # Nothing to execute — this is a terminal node
        continue

      IF node.type == "branch" or "step":
        # Evaluate outgoing edges
        outgoing = adj.get(node.id, [])

        # First: try conditional edges
        followed = False
        for edge in [e for e in outgoing if e["condition"] is not None]:
          if evaluate_condition(edge["condition"], test_data, results.get(node.id)):
            queue.append(node_by_id(edge["target"]))
            followed = True
            break    # first matching condition wins

        # Fallback: if no conditional edge matched, follow unconditional ones
        if not followed:
          for edge in [e for e in outgoing if e["condition"] is None]:
            queue.append(node_by_id(edge["target"]))

  STEP F — Aggregate results
    total   = count of step nodes that were visited and executed
    passed  = count where results[id] == "passed"
    failed  = count where results[id] in ("failed", "error")
    skipped = count where results[id] == "skipped"

  STEP G — Determine final run status
    if failed == 0:           status = "passed"
    elif passed > 0:          status = "partially_passed"
    else:                     status = "failed"

  STEP H — Update DB and notify
    run.status = final_status
    run.completed_on = datetime.utcnow()
    run.execution_summary = { total, passed, failed, skipped }
    db.commit()
    publish_to_TEST_SUITE_STATUS_QUEUE(run_id, final_status)

PART 13 — QUICK REFERENCE CHEAT SHEET
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  NODES
  ─────
  "start"  → Entry point. One per suite. No test runs here.
  "end"    → Exit point. Can have multiple. No test runs here.
  "step"   → Real test. Must link to page_id + scenario_id. Runs all test cases.
  "branch" → Decision diamond. No test. Only routes based on conditions.

  EDGES
  ─────
  condition = null        → Always follow this edge (unconditional)
  condition set           → Follow only if condition is true at runtime
  First match wins        → If multiple edges match, only the first is followed
  Fallback = unconditional → If no conditional edge matches, use unconditional

  CONDITIONS
  ──────────
  field = "_outcome"      → Looks at the result of the PREVIOUS step node
                             Values: "passed" | "failed" | "error" | "skipped"
  field = "anything_else" → Looks up that key in the test_data dict provided at run time
  op = "eq"               → equals
  op = "neq"              → not equals
  op = "in"               → value is in a comma-separated list

  TEST DATA
  ─────────
  Provided by the user when clicking "Run Suite"
  Example: { "role": "employee", "account_type": "corporate", "region": "IN" }
  Keys must match the "field" values used in conditions
  Does not change between steps — it is fixed for the entire run

  OUTCOMES
  ────────
  "passed"  → All test cases in the step's scenario passed
  "failed"  → One or more test cases failed
  "error"   → Script crashed (driver error, exception, timeout)
  "skipped" → Step node had no scenario linked

  RUN STATUS
  ──────────
  "pending"          → Queued, not started
  "running"          → Currently executing
  "passed"           → All executed steps passed
  "partially_passed" → Some passed, some failed
  "failed"           → All executed steps failed
  "error"            → Engine crashed before completing
